# Migrating to Beru

If you are a seasoned C++ developer, you have likely spent years fighting with raw CMake, writing custom `FindPackage.cmake` modules, or orchestrating complex builds with vcpkg and Conan. 

Transitioning to Beru requires a fundamental shift in mindset. In traditional workflows, the package manager and the build system are separate entities that you must bridge manually. **In Beru, the package manager *is* the build orchestrator.**

This chapter provides a deep, side-by-side comparison of common C++ workflows to help you map your existing knowledge onto the Beru model.

---

## 1. The Core Paradigm Shift

Before diving into code, it is critical to understand the architectural difference between Beru and its predecessors.

*   **vcpkg / Conan:** These are *dependency providers*. They download source code, compile it, and place the resulting binaries in a folder. It is then **your responsibility** to write the CMake code required to find those binaries, link them, and handle transitive dependencies.
*   **Beru:** Beru is an *orchestrator*. It reads your desired state (`Beru.toml`), calculates the dependency graph, compiles the dependencies, and **automatically generates the CMake integrations**. You do not write `find_package` calls; Beru writes them for you in a hidden toolchain file.

---

## 2. Adding a Third-Party Library

Let us compare the exact steps required to add the `{fmt}` formatting library to an executable project.

### 2.1. The vcpkg Workflow

vcpkg relies on CMake toolchains. To use it, you must maintain state in three different places: the CLI, the CMake script, and the build invocation.

**Step 1:** Install the library globally (or via a `vcpkg.json` manifest).
```bash
vcpkg install fmt
```

**Step 2:** Modify your `CMakeLists.txt` to locate and link the library. You must know the exact target name (`fmt::fmt`) that the library exports.
```cmake
# CMakeLists.txt
cmake_minimum_required(VERSION 3.15)
project(my_app)

find_package(fmt CONFIG REQUIRED)

add_executable(my_app src/main.cpp)
target_link_libraries(my_app PRIVATE fmt::fmt)
```

**Step 3:** Invoke CMake, explicitly passing the path to the vcpkg toolchain file. This path is often environment-dependent and hard to standardize across a team.
```bash
cmake -B build -DCMAKE_TOOLCHAIN_FILE=/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build build
```

### 2.2. The Conan Workflow

Conan improves upon vcpkg by using a manifest (`conanfile.txt`), but still requires significant CMake boilerplate.

**Step 1:** Declare the dependency in `conanfile.txt`.
```ini
[requires]
fmt/10.2.1

[generators]
CMakeDeps
CMakeToolchain
```

**Step 2:** Invoke Conan to resolve and install the dependencies.
```bash
conan install . --build=missing
```

**Step 3:** Modify your `CMakeLists.txt`. You must still manually find and link the package.
```cmake
# CMakeLists.txt
cmake_minimum_required(VERSION 3.15)
project(my_app)

find_package(fmt REQUIRED)

add_executable(my_app src/main.cpp)
target_link_libraries(my_app PRIVATE fmt::fmt)
```

**Step 4:** Invoke CMake, pointing it to the toolchain generated by Conan in Step 2.
```bash
cmake -B build -DCMAKE_TOOLCHAIN_FILE=build/generators/conan_toolchain.cmake
cmake --build build
```

### 2.3. The Beru Workflow

Beru eliminates the bridging boilerplate entirely. The manifest is the single source of truth.

**Step 1:** Declare the dependency in your `Beru.toml`.
```toml
# Beru.toml
[dependencies]
fmt = "10.2.1"
```

**Step 2:** Build the project.
```bash
beru build
```

**There is no Step 3.** 

When you run `beru build`, Beru automatically:
1. Fetches and compiles `fmt`.
2. Generates a hidden `beru-toolchain.cmake` that automatically calls `find_package` and sets up the linking targets.
3. Invokes CMake and injects the toolchain.

You never touch a toolchain path, and you never write a `find_package` call.

## 3. Managing the C++ Standard

Enforcing a specific C++ standard (e.g., C++20) across a large project and all of its dependencies is notoriously difficult and a frequent source of ABI (Application Binary Interface) bugs.

### 3.1. The CMake Approach

In raw CMake, you must explicitly set variables to control the compiler standard.

```cmake
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF) # Disable GNU extensions for portability
```

However, this only applies to *your* code. If you are using vcpkg or Conan, you must ensure that your dependencies were also compiled with C++20. If a dependency was compiled with C++14, linking it into your C++20 application can cause subtle, undefined behavior at runtime due to changes in standard library layouts (like `std::string` or `std::filesystem`).

### 3.2. The Beru Approach

In Beru, the C++ standard is a top-level metadata field.

```toml
[package]
cxx-std = "c++20"
```

Because Beru compiles your dependencies from source, it **propagates this standard** down the dependency graph. When Beru builds `fmt` for your project, it guarantees that `fmt` is compiled as C++20. Furthermore, Beru incorporates the `cxx-std` into its global cache key. This means Beru safely maintains separate cached binaries for the C++17 version of `fmt` and the C++20 version of `fmt`, completely eliminating ABI mismatch errors.

## 4. Coexisting with Legacy CMake

One of Beru's most powerful features is that it does not force you to abandon complex, custom CMake logic if you truly need it.

While Beru can auto-generate `CMakeLists.txt` for standard projects, it acts intelligently when it detects an existing `CMakeLists.txt` in your project root.

If you have a massive, 10-year-old `CMakeLists.txt` that handles custom code generation, Qt MOC compilation, or complex post-build scripts, you can still use Beru to manage your dependencies. 

1. Initialize Beru in your project (`beru init`).
2. Add your dependencies to `Beru.toml`.
3. Keep your existing `CMakeLists.txt` exactly as it is.

When you run `beru build`, Beru will resolve and compile the dependencies, and then invoke *your* `CMakeLists.txt`, passing `CMAKE_PREFIX_PATH` to ensure your existing `find_package` calls magically succeed. This allows for a graceful, incremental migration from legacy systems to the modern Beru ecosystem.
