# Reference: The Beru.lock Guarantee

In modern software development, "it works on my machine" is an unacceptable excuse. Teams require absolute assurance that the code they compile on a Tuesday will produce the exact same binary on a Friday, regardless of what third-party developers have published in the interim.

Beru achieves this via the `Beru.lock` file. This chapter explains the mechanics, the guarantees, and the version control strategies surrounding the lockfile.

---

## 1. The Anatomy of a Resolution

To understand the lockfile, you must understand the problem it solves. 

Suppose your `Beru.toml` contains:
```toml
[dependencies]
fmt = "10.2.1"
```

In the Semantic Versioning (SemVer) standard, requesting `10.2.1` usually implies a compatibility constraint (often written as `^10.2.1` in other ecosystems). It means you are willing to accept `10.2.2` or `10.3.0` (which contain backwards-compatible bug fixes and features), but you will not accept `11.0.0` (which contains breaking API changes).

If you run `beru build` today, the PubGrub algorithm might query the index and find that `10.2.5` is the highest published version matching your constraint. It downloads and compiles `10.2.5`.

Three months later, a new developer joins your team, clones the repository, and runs `beru build`. In those three months, the `fmt` authors published version `10.4.0`. Without a lockfile, the new developer's machine would evaluate the constraints, download `10.4.0`, and compile it.

**The Problem:** The two developers are now building against different source code. If `10.4.0` introduced a subtle performance regression or an accidental compiler warning, the team would experience divergent builds, leading to hours of frustrating debugging.

## 2. The Lockfile Solution

When Beru performs dependency resolution (either via `beru build` or `beru resolve`), it takes the final, computed graph of exact versions and writes them to a TOML file named `Beru.lock`.

```toml
# This file is automatically generated by Beru.
# It is not intended for manual editing.

[[package]]
name = "fmt"
version = "10.2.5"
source = "registry"
checksum = "312151a2d12c8336f5fc2e6cf8e2b4ceada06e599d4ee1537f732a5dfb0e2719"

[[package]]
name = "my_app"
version = "0.1.0"
dependencies = [
    "fmt 10.2.5",
]
```

When the new developer clones the repository and runs `beru build`, Beru sees the `Beru.lock` file. It **bypasses the resolution phase entirely.** It does not care that `10.4.0` exists. It reads the lockfile, sees that `10.2.5` is strictly required, verifies the cryptographic `checksum`, and compiles that exact version.

The build is now perfectly reproducible.

## 3. Version Control Strategies (When to Commit)

The most common question regarding lockfiles is: *"Do I check this file into Git?"*

In the Beru ecosystem (much like Cargo or npm), the answer depends entirely on the `type` of project you are building.

### 3.1. Building an Application (`type = "executable"`)
**Verdict: ALWAYS Commit.**

If you are building an executable binary, a CLI tool, or a deployable web server, you are producing a final, end-user artifact. You are at the very top of the dependency chain. 

You want absolute, deterministic control over the exact bits that are compiled into your release binary. If an upstream library releases a bugged patch version, you do not want your CI pipeline to automatically pull it in and break your deployment. You must commit `Beru.lock` to enforce this stability.

To update dependencies in an application safely, you run `beru resolve` manually, review the changes to the `Beru.lock` file in a Pull Request, and merge them intentionally.

### 3.2. Building a Library (`type = "library"`)
**Verdict: NEVER Commit (Add to `.gitignore`).**

If you are building a library, you are producing a building block for other people to use. You do not control the final build environment.

If another developer adds your library to their application, Beru will evaluate the constraints in your `Beru.toml`. **It will completely ignore your `Beru.lock` file.** 

Why? Because the top-level application must compile a single, unified dependency graph. If your library demanded `fmt 10.2.5` via its lockfile, and another library in the application demanded `fmt 10.3.0` via its lockfile, resolution would be impossible. The application must be free to find a version (like `10.3.0`) that satisfies both libraries' loose constraints simultaneously.

Committing a `Beru.lock` for a library creates a false sense of security for the library author (who is testing against locked versions that their downstream users will never actually experience) and clutters the repository.
